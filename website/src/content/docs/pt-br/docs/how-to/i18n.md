As strings de UI do Amarra vêm de um catálogo baseado em chaves em `pkg/cais/i18n`. `LOCALE` define o padrão, e cada request pode sobrescrevê-lo com `?lang=` ou o cookie `cais_locale` — é isso que o `<.locale-toggle />` do kit faz. Os templates leem as strings através de um par de funções de template; não há negociação de Accept-Language.

## Escolher um locale

Defina `LOCALE` no ambiente (ou no `.env` local):

```bash
LOCALE=en   # default
LOCALE=pt   # Portuguese
```

`cais.Config.Locale` é lido de `LOCALE` e usa `en` como padrão quando não definido. Os catálogos carregam uma vez no boot — `view.Load(fsys, catalog, en, pt)` para views Amarra — e um catálogo nil recorre a `DefaultCatalog()`.

## Trocar o locale por request

`i18n.LocaleMiddleware` resolve o locale a cada request: `?lang=` primeiro, depois o cookie `cais_locale`, depois o padrão configurado. O scaffold o conecta depois do `LoadSession`:

```go
r.Use(i18n.LocaleMiddleware(catalogs, cfg.Locale))
```

O `view.Write` renderiza o conjunto de páginas que corresponde ao catálogo do request. Os handlers traduzem o texto do request com `i18n.CatalogOr(r, h.catalog).T("contact.title")` em vez de capturar um catálogo no boot — um catálogo capturado no boot ignoraria o toggle de idioma.

O `<.locale-toggle />` do kit envia `locale=en|pt` para `/locale` via Drive, e o handler do scaffold guarda a escolha com `i18n.SetCookie`. Valores com região, como `pt-BR`, normalizam para o subtag primário (`pt`), e o toggle continua marcando o idioma ativo (`aria-pressed`).

## Usar strings nos templates

Os templates chamam `{{ t "key" }}` para traduzir, e `{{ htmlLang }}` / `{{ ogLocale }}` para emitir os códigos atuais de idioma e locale:

```html
<html lang="{{ htmlLang }}">
  <body>
    <h1>{{ t "contact.title" }}</h1>
  </body>
</html>
```

- `htmlLang` retorna a tag de idioma HTML (`en`, `pt-BR`).
- `ogLocale` retorna o locale do Open Graph (`en_US`, `pt_BR`).

Páginas e partials recebem as mesmas funções de template, então `{{ t }}` funciona em ambas. Os handlers recebem o `*i18n.Catalog` diretamente para validação e strings de flash, por exemplo `h.catalog.T("contact.title")`. Uma chave ausente retorna a própria chave, o que torna as lacunas visíveis durante o desenvolvimento.

## API do catálogo

```go
// pkg/cais/i18n
const DefaultLocale = "en"

func NewCatalog(locale string) *Catalog
func DefaultCatalog() *Catalog

func (c *Catalog) T(key string, args ...any) string
func (c *Catalog) HTMLLang() string        // "en", "pt-BR"
func (c *Catalog) OGLocale() string        // "en_US", "pt_BR"
func (c *Catalog) Funcs() template.FuncMap // t, htmlLang, ogLocale
```

```go
// locale por request (pkg/cais/i18n/request.go)
func LocaleMiddleware(catalogs map[string]*Catalog, fallback string) func(http.Handler) http.Handler
func CatalogForRequest(r *http.Request, catalogs map[string]*Catalog, fallback string) *Catalog
func CatalogFromRequest(r *http.Request) *Catalog
func CatalogOr(r *http.Request, fallback *Catalog) *Catalog
func SetCookie(w http.ResponseWriter, locale string, secure bool)
func SetCookieOpts(w http.ResponseWriter, locale string, opts CookieSettings)
```

`T` aceita argumentos opcionais para substituição na string.

## Adicionar ou estender um locale

Os catálogos ficam em `pkg/cais/i18n`:

- `locales/en.go` — todas as chaves, em inglês (o padrão).
- `locales/pt.go` — traduções em português, usadas quando `LOCALE=pt`.

Adicione uma chave em `en.go` primeiro, depois traduza-a em `pt.go`. Para adicionar outro locale, adicione um arquivo `locales/<code>.go` com as mesmas chaves e selecione-o com `LOCALE=<code>`. Passe todos os catálogos ao `view.Load` para que `?lang=` possa resolvê-los.

:::caution
Ainda fora do escopo: negociação de Accept-Language, pluralização e catálogos externos em JSON/YAML. As strings ficam em mapas Go sob `pkg/cais/i18n/locales/`.
:::
