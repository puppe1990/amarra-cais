Amarra and Cais share a lineage but ship different frontends. Knowing which product you have tells you which documentation applies and what a migration actually costs.

## The split

| Product      | Frontend                | Notes                        |
| ------------ | ----------------------- | ---------------------------- |
| Cais v0.11.x | Inertia + Svelte (Vite) | Frozen line, still supported |
| Amarra       | Amarra Views + Drive    | HTML-first fork of Cais      |

The CLI binary is `amarra-cais`, and it does not overwrite `cais`. You can have both installed side by side. Cais v0.11.x remains the Inertia product; apps generated by Amarra use server-rendered HTML in `web/templates/` with `/static/js/amarra.js` and no Vite.

This is not a dual-mode fork. `amarra-cais doctor` fails when it finds a `vite.config.js`, because an app is one or the other — there is no `--front inertia` flag.

## Migrating is a UI rewrite

Moving a Cais Inertia app to Amarra is not a `go get`. The data layer stays; the UI layer is rewritten.

1. Pin the framework (`go get github.com/puppe1990/amarra-cais@v0.11.0`) and remove gonertia. Delete `vite.config.js`, `svelte.config.js`, `web/src/`, and `web/static/build/`.
2. Load views once at boot with `view.Load`. Handlers take a `*view.Renderer` and call `view.Write`; they no longer check `HX-Request` or call Inertia render helpers.
3. Replace pages: `web/src/pages/*.svelte` becomes `web/templates/pages/*.html`, `AppLayout.svelte` becomes `web/templates/layouts/app.html`, and the `#app` mount becomes `#amarra-main` plus one script. Svelte forms become kit `<.form>` / `<.input>` / `<.button>`.
4. Rewrite tests to assert HTML (`testutil.AssertHTMLContains`) instead of Inertia JSON. Drop `setupTestInertia` and `X-Inertia: true`.
5. Keep `httpx.ParseFormOrJSON` — Drive posts form-encoded or multipart bodies.
6. Use the cookie flash API: `flash.Set(w, kind, msg, cfg.CookieSecure())` then a `303`.
7. Refresh PWA assets with `amarra-cais pwa`, then `amarra-cais pwa --bump` after template changes.
8. Rename CLI calls: `cais new` → `amarra-cais new`, `cais g` → `amarra-cais g`, `cais doctor` → `amarra-cais doctor`, `cais pwa` → `amarra-cais pwa`.

What stays: your store, SQLite migrations, jobs and `/jobs`, domain packages, session/CSRF/rate-limit middleware, and even the CSRF cookie name (`cais_csrf` / `__Host-cais_csrf`). You are rewriting the UI, not the data layer.

:::caution
Plan the migration page by page. A suggested order is to scaffold `amarra-cais new scratch`, copy the layout and view-data helpers, then move one public page (home or login) end to end before repeating for the rest.
:::

Continue with the [upgrade guide](/amarra-cais/docs/how-to/upgrade/) and [pages and views](/amarra-cais/docs/how-to/pages-and-views/), or read [Views and Drive](/amarra-cais/docs/explanation/views-and-drive/) for the design behind the target frontend.
