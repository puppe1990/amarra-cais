Amarra's UI strings come from a key-based catalog in `pkg/cais/i18n`. `LOCALE` sets the default, and each request can override it with `?lang=` or the `cais_locale` cookie — that is what the kit `<.locale-toggle />` does. Templates read strings through a pair of template functions; there is no Accept-Language negotiation.

## Choose a locale

Set `LOCALE` in the environment (or the local `.env`):

```bash
LOCALE=en   # default
LOCALE=pt   # Portuguese
```

`cais.Config.Locale` is read from `LOCALE` and defaults to `en` when unset. Catalogs load once at boot — `view.Load(fsys, catalog, en, pt)` for Amarra views — and a nil catalog falls back to `DefaultCatalog()`.

## Switch the locale per request

`i18n.LocaleMiddleware` resolves the locale for every request: `?lang=` first, then the `cais_locale` cookie, then the configured default. The scaffold wires it after `LoadSession`:

```go
r.Use(i18n.LocaleMiddleware(catalogs, cfg.Locale))
```

`view.Write` renders the page set that matches the request catalog. Handlers translate request copy with `i18n.CatalogOr(r, h.catalog).T("contact.title")` instead of capturing a catalog at boot — a catalog captured at boot would ignore the language toggle.

The kit `<.locale-toggle />` posts one `locale=` value per button to `/locale`. Default buttons are `en` and `pt`; pass `locales="en,pt,es"` or page data `.Locales` (`[]string`) to add catalogs such as `es` and `zh`. Forms use `data-amarra-skip` so the locale cookie applies on a full navigation. The scaffold handler stores the choice with `i18n.SetCookie`. Region-qualified values such as `pt-BR` normalize to the primary subtag (`pt`), and the toggle still marks the active language (`aria-pressed`).

## Use strings in templates

Templates call `{{ t "key" }}` to translate, and `{{ htmlLang }}` / `{{ ogLocale }}` to emit the current language and locale codes:

```html
<html lang="{{ htmlLang }}">
  <body>
    <h1>{{ t "contact.title" }}</h1>
  </body>
</html>
```

- `htmlLang` returns the HTML language tag (`en`, `pt-BR`).
- `ogLocale` returns the Open Graph locale (`en_US`, `pt_BR`).

Pages and partials receive the same template functions, so `{{ t }}` works in either. Handlers get the `*i18n.Catalog` directly for validation and flash strings, for example `h.catalog.T("contact.title")`. A missing key returns the key itself, which makes gaps visible in development.

## Catalog API

```go
// pkg/cais/i18n
const DefaultLocale = "en"

func NewCatalog(locale string) *Catalog
func DefaultCatalog() *Catalog

func (c *Catalog) T(key string, args ...any) string
func (c *Catalog) HTMLLang() string        // "en", "pt-BR"
func (c *Catalog) OGLocale() string        // "en_US", "pt_BR"
func (c *Catalog) Funcs() template.FuncMap // t, htmlLang, ogLocale
```

```go
// per-request locale (pkg/cais/i18n/request.go)
func LocaleMiddleware(catalogs map[string]*Catalog, fallback string) func(http.Handler) http.Handler
func CatalogForRequest(r *http.Request, catalogs map[string]*Catalog, fallback string) *Catalog
func CatalogFromRequest(r *http.Request) *Catalog
func CatalogOr(r *http.Request, fallback *Catalog) *Catalog
func SetCookie(w http.ResponseWriter, locale string, secure bool)
func SetCookieOpts(w http.ResponseWriter, locale string, opts CookieSettings)
```

`T` accepts optional arguments for substitution into the string.

## Add or extend a locale

Catalogs live under `pkg/cais/i18n`:

- `locales/en.go` — every key, in English (the default).
- `locales/pt.go` — Portuguese translations, used when `LOCALE=pt`.

Add a key to `en.go` first, then translate it in `pt.go`. To add another locale, add a `locales/<code>.go` file with the same keys and select it with `LOCALE=<code>`. Pass every catalog to `view.Load` so `?lang=` can resolve it.

:::caution
Still out of scope: Accept-Language negotiation, pluralization, and external JSON/YAML catalogs. Strings live in Go maps under `pkg/cais/i18n/locales/`.
:::
